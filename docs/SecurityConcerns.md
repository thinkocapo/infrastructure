# Security Concerns

**Docker socket access — mitigated, not eliminated.** `-collectors=docker` (Fleet-Wide) needs *something* to read the Docker Engine API, and mounting `/var/run/docker.sock` directly into the monitor's container is root-equivalent access to that host — a process with access to that socket can create, exec into, or mount the host filesystem into any container. `docker-compose.yml` now fronts the real socket with a read-only proxy ([`tecnativa/docker-socket-proxy`](https://github.com/Tecnativa/docker-socket-proxy)) instead: only `CONTAINERS=1` is enabled (list + stats, both GET), everything else (exec, create, mount, volumes, networks, ...) stays off by default, and `infra-monitor` itself ends up with *zero* Docker socket mount — verified via `docker inspect`. `infra-monitor` talks to the proxy over `DOCKER_HOST=tcp://docker-proxy:2375` instead, which required no code changes at all, since the Docker client already reads `DOCKER_HOST` from its environment. Still worth raising explicitly with whoever owns security for a given environment — a read-only proxy narrows the blast radius, it doesn't make socket access a non-issue — but it's a real mitigation now, not just a caveat to accept.

**Per-Target vs. Fleet-Wide tradeoff.** Choosing Per-Target means running one process per target instead of one process watching the whole fleet — more instances to deploy and update, in exchange for no socket exposure and no all-or-nothing visibility. `-collectors=docker` stays fully available in this same binary for local testing or any environment where the socket tradeoff is acceptable — [open a feature request](https://github.com/thinkocapo/infrastructure/issues/new) if there's something you'd like to see to make this more usable for you.

**Container scoping as a data-governance question — fixed for the direct SDK, still partial for OTel.** Fleet-Wide reporting metrics (and container names) for another team's workload on a shared host, without their knowledge, isn't just a feature gap — it's a real data-governance question. The direct SDK's Fleet-Wide path now has a `CONTAINERS` env var (comma-separated container names) as a real allow-list, verified live: with it unset, a test run reported on unrelated containers from a completely different project on the same host; with `CONTAINERS` set, it reported on only the named ones. OTel Collector mode still only has `dockerstatsreceiver`'s `excluded_images` (image-based exclusion), not a name-based allow-list — worth a real conversation with whoever owns that host before running Fleet-Wide there in OTel mode.
